# Phase 6.1 maintenance reliability — 2026-09-27

The user approved proceeding with the first Phase 6 increment. Maintenance reliability and export safety are implemented locally. Technician job cards and subsequent increments remain planned.

## Delivered behavior

- Maintenance creation, vendor creation, status/assignment changes, work-order costs and preventive-plan creation now use domain actions under `app/Domain/Operations/Actions`. Each mutation and its audit event share a transaction. Updates lock and reload the organization-owned record.
- Status-only updates preserve the assigned member; explicitly sending a null assignee unassigns the request. Repeated completion preserves its original completion timestamp. Existing statuses and manager authority remain available; a new closure/reopening approval policy has not been introduced.
- Preventive generation requires the displayed occurrence date as `due_on` in `YYYY-MM-DD`. The action locks and reloads the plan, verifies its current due occurrence, and atomically creates the request, advances the schedule and records the audit event.
- Requests generated by this workflow carry the plan ID and occurrence date. A database unique constraint prevents multiple requests for the same plan/date. A retry returns the existing request without advancing again, including when the next occurrence is also overdue. A stale request for an ungenerated occurrence is rejected with a refresh message.
- Due eligibility uses the organization's current local date. The generated deadline is the end of that local day stored in UTC. Plan dates serialize as calendar dates; the page uses the server-provided local date, disables generation while a request is pending and displays validation errors.
- Each manual generation still handles one occurrence and advances from that scheduled date by the configured interval. Scheduled generation and changes to missed-occurrence policy are deferred to their own increment.
- Generic maintenance, inventory, leads and receivables CSV exports use their module's view permission. Data selection lives in module-owned queries, CRM visibility remains enforced, and user-controlled spreadsheet formula prefixes are escaped. Receivables retains its existing invoice-summary columns; it is not a replacement for the dated outstanding-balances report.
