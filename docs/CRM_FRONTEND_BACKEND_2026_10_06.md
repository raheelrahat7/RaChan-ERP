# CRM frontend backend contract — 2026-10-06

All routes below use authenticated, organization-scoped web requests. Send `Accept: application/json` for JSON on `GET /crm/contacts`; the existing browser page remains Inertia. Validation failures use Laravel's `422 {message,errors:{field:[message]}}` response.

## Parties and qualified lead picker

- `GET /crm/contacts?q=&per_page=` → `{contacts: paginator}`; `GET /crm/companies?q=&per_page=` → `{companies: paginator}`. Both page sizes default to 25 and max at 100. Items include `version` and `permissions:{read,edit}`.
- `POST /crm/companies` accepts `{name,email?,phone?,website?}` and returns the company detail shape with HTTP 201. Existing `POST /crm/contacts` also returns the contact detail shape with HTTP 201 for JSON requests; browser requests retain their redirect.
- `GET /crm/contacts/{id}` → `{contact,customFields,leads,deals,activities}`; `GET /crm/companies/{id}` → `{company,customFields,leads,deals,activities}`. The party object includes `version`, `permissions`, and its account/contacts relation. Activities are paginated; linked leads are visible converted leads, and linked deals obey deal access and amount visibility. `customFields` has the existing `ManageRecordFields::values` shape.
- `PUT /crm/contacts/{id}` accepts `expected_version` plus optional `first_name,last_name,email,phone,account_id,custom_fields`. Use `account_id:null` to unlink. `PUT /crm/companies/{id}` accepts `expected_version` plus optional `name,email,phone,website,custom_fields`. Both return the corresponding detail payload and increment `version`. A stale version produces `errors.expected_version`; a foreign `account_id` produces `errors.account_id`. The separate `PUT /crm/records/{entity}/{record}/fields` also requires `expected_version` and now returns `{fields,version}`.
- `GET /crm/leads/qualified?q=&per_page=` → `{leads:paginator}` with `{id,name,stage:{id,name},assignee:{id,name}|null,amount,permissions}`. Eligibility matches deal creation: active pipeline, active Won stage, no existing deal, and lead visibility. `amount` is the first visible currency custom field's numeric value, or `null`.
- `GET /organization/crm-catalog/products` lets users with CRM edit permission read **active** products. Administrators still see inactive products. POST/PUT catalog writes remain `manageSettings` only.

## Deals and finance links

- `PUT /crm/deals/{id}/transfer` and existing POST alias accept `{expected_version,pipeline_id,stage_id,confirmed:true,notes?,lost_reason?}`. The destination must be a different active pipeline and its active stage. Reopening a final deal requires `notes`; entering a lost stage requires `lost_reason`. Response is `{deal}` exactly as stage movement, with incremented `version` and permissions.
- `POST /crm/deals/{id}/financial-links` and existing PUT alias accept `{kind:"invoice"|"commission",record_id,expected_version,remove?:boolean}`. Both require deal edit and amount access, plus finance or transaction permission for the respective kind. Response: `{financialRecords:{invoices:[{id,reference,status,total,currency,received,outstanding}],commissions:[{id,status,commission_amount,currency,paid_on}]},version}`. Financial arrays are empty when the caller lacks amount or module read access.

## Automation

- Lead rules (`GET /crm/automation`, Inertia props) offer triggers `stage_entered,lead_created` and actions `notify_assignee,notify_managers,create_follow_up,change_stage`. Rule input uses `name,pipeline_id,stage_id?,trigger,condition_field?,condition_operator?,condition_value?,action,delay_minutes?,activity_type?,target_stage_id?,due_days?,active?`. Operators are `equals,not_equals,contains,empty,not_empty`. Change-stage requires an active normal destination; follow-up requires `due_days`. `executionHistory` is the latest 100 executions.
- Deal rules (`GET /crm/deals/automation`, JSON) offer stage-entry rules with `actions:[notify_assignee,notify_managers,create_follow_up,change_stage]`, `rules`, and paginated `executions`. Save with `name,pipeline_id,stage_id,action,active,delay_minutes` and optional `conditions` (the deal filter condition array), `working_hours_only`, `target_stage_id`, `activity_type`, `due_days`. The target stage must be another active normal stage in the pipeline. `delay_minutes` is 0–525600; `due_days` is 0–365. There is no test-run endpoint; execution history is the log.

## Estimates, calendar, providers, and remaining tiles

- Create a lead-linked estimate with `POST /reference-workflows`: `{pipeline_id:<estimate pipeline>,title,assigned_to,operation_key:<UUID>,lead_id,contact_id?,details:{currency,valid_until?,notes?,lines:[{description,quantity,unit_price}]}}`. The response `{record}` includes `id,lead_id,version,permissions` (and calculated details). To list linked estimates use `GET /reference-workflows?kind=estimate` and filter `records.data` by `lead_id`; `GET /crm/leads/{id}/products` also supplies the lead's product and estimate links. A separate create-estimate helper is unnecessary because this endpoint already performs the lead link and validation.
- `POST /reference-workflows/{record}/invoice`: `{expected_version,due_on:"YYYY-MM-DD",accounting_treatment:"revenue"|"refundable_deposit",vat_treatment?:"standard"|"zero_rated"|"exempt"|"out_of_scope"}`. `vat_treatment` is required when VAT is enabled. The estimate must be accepted, current-version, AED, and accessible; caller needs finance management. Response `{invoice}` includes the new draft invoice `id` and `reference`. Repeating after conversion returns the linked invoice.
- `GET /crm/settings/calendar` → `{calendar:null|{working_days:{"1":{start:"09:00",end:"17:00"},...},holidays:["YYYY-MM-DD"],timezone,version,permissions:{read,edit}}}`. Day keys are ISO weekdays 1–7. `PUT` accepts `{expected_version,working_days,holidays}` and returns `{saved:true,version,permissions:{read:true,edit:true}}`. Use `expected_version:0` when the calendar is null; otherwise use the fetched version. The calendar is organization-local; only owner/administrator can change it.
- `GET /organization/reference-settings/providers` → `{kind:"providers",records:[{id,organization_id,capability,name,provider,active,settings,version,permissions:{read,edit},...}],providerCapabilities:["sms","payment","accounting_export","email","whatsapp","property_portal","signature"],deliveryEnabled:false}`. POST/PUT profile input is `{capability,name,provider?:string|null,active:false,settings?:{sender?,label?,print_title?,terms?,daily_limit?}}`; PUT additionally requires `expected_version`. Both return `{id,version,permissions:{read:true,edit:true}}`. Profiles remain local and inactive while providers are unselected.
- Other Settings now has `GET/POST /organization/crm-catalog/other-settings` and `PUT /organization/crm-catalog/other-settings/{id}`. It stores organization-scoped, audited display preferences as `{code,name,active,position?,settings:{value:string,description?:string}}`; no business rule is inferred from a preference. Rows include `version`; PUT additionally requires `expected_version` and returns the incremented version. Other existing catalog kinds retain their legacy request shapes. CRM applications market is outside this local CRM backend scope because an installable external application catalog and permissions model have not been selected.

Every newly versioned party, Other Settings, calendar, and provider profile update requires `expected_version`. Stale writes return HTTP 422 with `errors.expected_version` and preserve the saved record. Calendar/provider details are in [CRM_FRONTEND_BACKEND_SETTINGS_LOCKING_2026_10_06.md](CRM_FRONTEND_BACKEND_SETTINGS_LOCKING_2026_10_06.md). No external provider delivery is enabled.
