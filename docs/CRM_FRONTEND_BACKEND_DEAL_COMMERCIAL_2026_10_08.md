# Deal commercial tracking contract

Deal status is separate from the sales pipeline stage. It is an editable tracking label only. Setting `payment_received`, `commission_approved`, or `commission_paid` does not post a payment, approve an allocation, or change a linked finance record. Use `financialRecords` and the finance workflows for authoritative financial state.

## Deals

- `POST /crm/deals` accepts the existing required `title`, `category`, `pipeline_id`, plus optional `deal_status`, `scenario`, `gross_commission`, `co_broker_share`, `agent_share`. Example: `{"title":"Villa 1","category":"secondary","pipeline_id":3,"deal_status":"submitted","scenario":"co_broker","gross_commission":"15000.00","co_broker_share":30,"agent_share":40}`. Response `201 {"deal":{"id":12,"version":1,"deal_status":"submitted","scenario":"co_broker","gross_commission":"15000.00","co_broker_share":"30.00","agent_share":"40.00","permissions":{"read":true,"edit":true,"amount":true,...},...}}`.
- `PUT /crm/deals/{id}` accepts any subset of those fields with required `expected_version`. Example: `{"expected_version":1,"deal_status":"approved","gross_commission":"18000.00"}`. Response `200 {"deal":{..."version":2,...}}`.
- `GET /crm/deals/{id}` returns `deal` with the same fields and `permissions`, plus `dealStatusOptions` and `dealScenarioOptions`, each `[{"code":"submitted","name":"Submitted","active":true,"id":null},...]`. `GET /crm/deals` and `GET /crm/deals/configuration` also expose both option arrays. Organization overrides supply a numeric `id`.
- `gross_commission` is a nonnegative decimal with at most 2 places. Shares are percentages in `[0,100]`, with a combined maximum of 100. All are nullable. These are planning figures; they do not calculate or update finance allocations. The three figures are omitted from deal serialization unless `permissions.amount` is true. A user needs `permissions.add` to create, `permissions.edit` plus `expected_version` to update, and `permissions.amount` to write/read financial figures. `permissions.read` controls retrieval. `version` increments on update; create returns version 1.

## Organization choices

The existing `GET /crm/settings/data` returns `lists` containing `deal_statuses` and `deal_scenarios`. Owners/administrators use the existing selection-option create/update route and body: `POST /crm/settings/options` or `PUT /crm/settings/options/{id}` with `{"list_key":"deal_statuses","code":"legal_review","name":"Legal Review","position":14,"active":true}`. The `code` is required for a new deal-status/scenario option, unique within its list, and immutable after creation. On first edit, defaults are materialized so they remain editable; before that the deal endpoints expose defaults directly. Responses retain the existing `{ "option": {...} }` shape. Scenario defaults: `direct`, `co_broker`, `referral`, `other`. Status defaults: `submitted`, `approved`, `contract_in_progress`, `contract_signed`, `invoice_generated`, `payment_pending`, `payment_received`, `commission_calculated`, `commission_approved`, `commission_paid`, `disputed`, `clawback_required`, `refund_required`.

The selection-option record has no version/`expected_version` contract; deal records do. Invalid option codes, bad percentages/amounts and combined shares return `422 {"message":"...","errors":{"deal_status":["..."],"agent_share":["..."]}}` with the relevant field key. Stale deal writes return the same shape with `errors.expected_version`. Unauthorized writes return 403; an inaccessible deal returns 404. Selection-option writes require owner/administrator.
